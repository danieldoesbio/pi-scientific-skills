## Grades

- **success:** the target reached the model in attempt 1.
- **partial-success:** reached in attempt 2.
- **functional:** reached in attempt 3.
- **fail:** not reached in 3 attempts.

A reach through `sci_find`, a bash command, or a file read counts. A
`sci_find` reach counts at any rank in the result. The model sets the limit
(default 8, maximum 20), and the response stops on reach, so a low-ranked
reach scores the same as rank 1. The report therefore adds the target's rank
at reach. (In practice the limit was 8 in 117 of 183 calls, 100 of them with
no limit argument, and 20 in 14. The worst rank at reach was 8. See
"sci_find analysis".) A timeout uses up its attempt, and the summary flags
it. Core and non-Core are reported apart. Harness errors (`no-run`, `supervisor-error`) are kept apart from
grades.

## Protocol decisions, in order

1. **No skills in the prompt.** The first pilots loaded the Core skills into the
   system prompt. We changed to `--prompt-skills none`, so that every reach
   comes from search.
2. **Timeout is an attempt, not an error.** A response that runs past 1200 s
   ends its attempt, and that attempt counts. No tool-call limit: a limit would
   raise the score, not make it more accurate.
3. **Recovery lines.** The summary reports the response in which the target
   reached the model, and splits attempts by first `sci_find` call (response 1,
   later, never). This shows whether a model that does not search at once ever
   recovers.
4. **Persona pointer, not added.** We asked whether the persona may point to
   the package when the model asks where to look. Decision: not for now. The
   persona stays blind and never names a skill.
5. **Probe-invalid.** If the model did not need the skill to answer the
   request, the probe does not test search. That probe is sent back for a
   rewrite and is not scored against the model. A Fable judge decides this
   (`scripts/lib/probe-check.mjs`), because the blind persona accepts any
   plausible answer.
6. **Raw grades stay visible.** The summary prints the adjusted grades
   (probe-invalid left out) and a raw line (probe-invalid at its raw grade).
7. **Untestable.** `autoskill` needs a running screenpipe daemon and the user's
   screen history. The sandbox cannot supply them, and the request cannot be
   stated without them. It is declared untestable, with evidence in
   `testing/README.md`. Coverage is 161 of 162.
8. **Judge extended mid-run.** At the start of the full run, the judge ran
   only on probes graded `fail`. During the run, we extended it to every graded
   probe with an attempt that the persona ended satisfied before any wanted
   skill reached the model. The running process still uses the fail-only rule.
   `scripts/check-probes.mjs` applies the new rule after the run, from the kept
   transcripts. The final numbers come from that check.

## Observations

### Queries restate the prompt

The model's `sci_find` queries mostly restate the probe's long, specific
wording. The score therefore measures "does the model search" more than "can
it turn a vague need into a good query". A later run with shorter, vaguer
probes would measure the second.

### `consciousness-council`: probe-invalid

- The mid-run check and the final check both say invalid.
- a1: the query was about the topic (lab strategy, research ethics), not the
  format (a structured debate). The model read `scientific-brainstorming`, wrote
  the debate itself, and the persona ended satisfied.
- a2: the query named the format ("structured debate … council of
  perspectives") and reached the target.
- Judge: the a1 answer already gave the multi-voice debate the skill would
  give. Gap: none. The probe needs a rewrite so that the request needs
  something the skill has and a model does not.
- The mechanical miss split counts a1 as an index gap: `consciousness-council`
  was not in the top 20 for the a1 query. The query described the lab
  decision, not the format, so this says little about the index. Because the
  probe is invalid, the analysis below leaves it out.

### `dask`: valid partial-success

- a1: no search. The model answered from memory in one response, and the
  persona ended satisfied.
- a2: searched at once and reached the target.
- Judge: needed. The judge says the a1 code used an argument
  (`dd.read_csv(..., npartitions=64)`) and a scheduler config call
  (`dask.config.update({"distributed.scheduler": "threads"})`) that do not
  work, and that the skill's examples would have fixed both. I did not verify
  these API claims against the dask docs. If they hold, this is the case the
  judge exists for: the persona accepted broken code.

### `database-lookup`: reached by `read`

The model looked through the pi docs with bash, listed the skills directory,
and read `database-lookup/SKILL.md` directly. This counts under the rules
(a reach through a file read), but it is not a `sci_find` reach.

### `esm`: the search does not find the skill

- Result: fail. All three attempts ended by timeout, so the probe check did
  not run (it looks only at attempts the persona ended).
- In a1 and a2 the model called `sci_find` three times, with queries close to
  the task. `esm` was **not in the top 20 hits** of any of them. `tamarind`
  (a cloud platform that runs ESM and other models) ranked 2nd, 7th and 1st.
  In a3 it searched twice more ("fill in masked regions of a partial protein
  sequence with a generative protein model"; "predict all-atom 3D structure
  from a protein sequence"). Every attempt read only `tamarind`.
- a3 response 1 ended before the limit. The persona then said it had no
  Tamarind key and asked for a script and example payloads. Response 2 ran
  to the 1200 s limit.
- The model then read the tamarind skill and spent the rest of each 1200 s
  response trying to run it: it checked for `TAMARIND_API_KEY`, listed the
  environment and home directory, grepped for keys, and tried `curl` to the
  internet.
- The sandbox held. No key was found (the rc-file grep returned nothing, and
  the provider config has only placeholder keys). DNS failed, and no request
  left the machine.
- Likely cause: the `esm` description names only the SDK and model IDs
  ("Use when working directly with the `esm` Python SDK, ESM3 or ESMC model
  IDs, Forge/Biohub inference clients, or ESMFold2 folding workflows"). It has
  no words for what the skill does (masked sequence generation, structure
  prediction). A search from a need cannot match it. This is a skill-metadata
  finding, not a model failure. I have not tested a changed description.
- Direct check of the index (`search()` from `extensions/search.ts`, limit 20,
  no model):

  | Query | `esm` rank |
  |---|---|
  | the a1 query (masked regions … all-atom 3D structure) | not in top 20 |
  | predict protein 3D structure from sequence all-atom | not in top 20 |
  | predict protein structure from sequence | 2 |
  | protein language model embeddings | not in top 20 |
  | masked protein sequence generation | not in top 20 |
  | ESM3 | 1 |
  | esm protein model | 1 |

  `esm` ranks only when the query names it, or when an existing alias in
  `extensions/aliases.ts` fires. That alias matches the phrases "protein
  structure", "structure prediction", "protein folding", "fold a protein" and
  "alphafold", and surfaces `esm` and `tamarind`. The model's queries said
  "all-atom 3D structure" and "protein 3D structure", so the alias did not
  fire. No alias covers masked generation or protein language models.
  The query "esm3 protein" returns no hits at all: "esm3" matches only the
  description (1 point), and two-word queries need 2. This
  is an observed miss of the kind `aliases.ts` asks for as evidence. No change
  was made: a change to search now would change what later runs measure.
- The probe's `accept` list is empty, so a reach of `tamarind` does not count.

### `fluidsim`: reasoning spills into the answer after the thinking cap

- a1 was one assistant message with no tool call. It never finished, so pi
  wrote no session file for it. The raw event stream (`a1-r1.jsonl`, 20,277
  events) holds all of it.
- Thinking: 22,799 characters. This is about the size of the 8192-token cap,

- Then 33,784 characters of visible text, which is still reasoning ("The user
  wants help with … Let me think about what's actually needed here"). It

  limit. No line repeats more than 3 times: this is long reasoning, not a
  loop.
- a2: `sci_find` first ("spectral method turbulence simulation solver
  selection CFL time step resolution check"), reached in 14 s.
- Possible test-condition effect: when thinking reaches the cap, the model
  can keep reasoning in the visible text, where no cap applies. The post-run
  check of all 18 timed-out attempts found this pattern only here (see
  "Timeouts").

### `genomic-intelligence`: the persona accepted a probably invented tool

- a1: no tool calls. The persona said the sequence is an unannotated 8 kb

  "GeneMark-PL web" at `https://www.gene-mark.com/` and described its GFF

- The persona ended the attempt with "assistant named a specific hosted

- a2: `sci_find` first, reached in 98 s.
- Final check: valid. Judge: the scientist asked for a hosted model that

### Sandbox notes

- The sandbox passes `PATH` through, and `PATH` contains home-directory names.
  A model that lists its environment sees them. No change was made; flagged
  for a decision.
- **`open-notebook` a1 (probe 84) probed the sandbox from the inside.**
  - It found `ollama` on the host, and `pgrep` showed a running ollama process.
    `ps` was denied. Its connection to ollama's port 11434 was denied.
  - It ran `ollama serve`. ollama made a new SSH key pair, which went into the
    attempt's fake HOME (`runs/open-notebook/a1/home/.ollama/`), not the real
    `~/.ollama`. The bind to 11434 was denied.
  - Writes to `/tmp` were denied; writes in the workspace worked. `lsof`
    listed the host's listening processes by name.
  - A port scan found only 127.0.0.1:8090 open: **the model's own inference
    server**. The model then sent 3 chat completions to it with `curl` and got
    answers. This works because the server slot is idle while a tool runs.
    The sandbox cannot let pi reach 8090 and keep pi's child processes out.
    The model gains no new knowledge this way (it is the same model), but it
    costs time, and it is a route to self-delegation. No change was made.
  - The disk report in its first command showed the host disk 96% full
    (42 GiB free).
  - Summary: the sandbox held for files and network. It does not hide host
    process names or the model's own server.
- **`parallel-web` a1 (probe 92) tried to install a launchd job.** The
  request asked for a recurring check. The model wrote a plist for label
  `com.pi.test` (program `/bin/true`) and ran `launchctl load` on it. The
  load failed with "Input/output error", probably because the path was wrong
  (no `.plist` suffix). The old profile did not deny `launchctl`: a loaded
  job runs through launchd, outside the sandbox. `osascript` and `open` were
  also allowed.
- **Post-run host check** (2026-09-24): no new launchd labels against a
  baseline taken during the run, no crontab, and no file in
  `~/Library/LaunchAgents` changed after the run started. Across all 161
  probes, only `parallel-web` a1 used a host-control program.
- **Fix, after the run** (commit `b304f8b`): the profile now denies
  `launchctl`, `open`, `osascript`, `automator` and `shortcuts`, and denies
  Apple events. Tested under the new profile: these are denied, also from a
  Python subprocess; `python3`, `node`, workspace writes, the server health
  check and `pi --version` still work. The fix applies to later runs only.
  This run used the old profile.

## sci_find analysis

An offline analysis (Opus 5.5 agent, then rerun on the final results). It
reads the results and transcripts and replays the model's own queries through
`search()`. It sends no request to the model server. Interim runs at n = 46
and n = 62 pointed the same way. The scripts are `run-all.sh`, `replay.mjs`,
`rank-at-reach.mjs`, `misses.mjs`, `stress.mjs`, `no-search.mjs`,
`alias-audit.mjs` and `whatif.mjs`; the archive keeps them and their output.

**Headline.** When the model searches, `sci_find` finds the target. The main
loss is attempts that do not search. On the 157 valid probes, 19 attempts
missed the target: 15 never called `sci_find`, 3 were the `esm` index gap,
and 1 was the limit (`simpy` a1).

**Replay is exact.** Offline `search()` gives the same text as the live tool
for 183 of 183 calls. Search changes can be tested offline on the model's
real queries.

**Rank at reach** (156 `sci_find` reaches, all 161 probes):

| Rank | Reaches |
|---|---|
| 1 | 125 |
| 2–3 | 24 |
| 4–8 | 7 |
| 9–20 | 0 |

- No reach needed a limit above 8. The worst were `research-lookup` (rank 8
  at limit 10) and `molfeat` (rank 7).
- Limit per call: 5 in 1 of 183, 8 in 117 (100 with no limit argument), 10
  in 34, 12 in 14, 15 in 3, 20 in 14.
- Two queries had the target at rank 9–20, outside the limit the model
  asked for: `simpy` a1 (rank 13 at limit 8; the attempt timed out) and
  `umap-learn` (rank 11 at limit 8; the next query found it). A default
  limit of 20 would have made `simpy` a success. One case is not enough to
  change the default.

**Misses, all 29 attempts without a reach** (the 10 on probe-invalid probes
included):

| Cause | Attempts |
|---|---|
| Never called `sci_find` | 24 (15 on valid probes) |
| Called it; target not in the top 20 (index gap) | 4: `esm` a1–a3, `consciousness-council` a1 (probe-invalid) |
| Target in the top 20, below the model's limit | 1: `simpy` a1 |

**Does the score depend on the probe wording?**

- The model's first queries copy 77% of their content words from the probe
  task. Pasting each probe task as the query puts the target in the top 8
  for 155 of 162 probes.
- **Name words.** 86 of 156 reaching queries contain a word of the target's
  name, and in 38 of them the probe task supplied that word. With those words
  removed (synthetic `noname` rewrite), the target stays in the top 8 for
  149 of 161 queries, against 155 of 161 for the original. The result does
  not rest on name leaks.
- **Generic wording.** With only common words left (DF ≥ 10, synthetic
  `generic` rewrite), the target is in the top 8 for 67 of 161. This run
  measures "does the model search" and "are there index gaps" well. It
  measures ranking for vague needs poorly.

**Why the model does not search.** First tool of response 1: `sci_find` 93,
bash 88, `read` 2, none 3. Of the 25 attempts with no `sci_find` call, 20 never
name it in their thinking. Five name it and still build first: `dask` a1,
`database-lookup` a1, `open-notebook` a1, `parallel-web` a1 and a2. The
no-search attempts are mostly build or setup tasks (EDA, MATLAB migration,
Modal deploy, podcast pipeline, web monitor, Polars ETL, pysam, Lightning
refactor). pi's system prompt never names `sci_find`: pi lists a custom tool
under "Available tools" only when it has a `promptSnippet`, and `sci_find` has
none. The model sees the tool only in its schema. In `dask` a1 the thinking
weighed `sci_find` and declined: the task was not "a 'scientific skill'
task like variant calling or fitting a survival model". Those are the two
examples in the tool description (`extensions/index.ts`). The examples may
set the model's idea of what the tool is for.

**Alias side effects.** The alias boost (+4) put another skill above the target
in 18 reaches below rank 1. Triggers that fire off-topic in real queries:
"references" (reference frame, coordinate reference system, reference SNP
ID; `astropy` and `geopandas` at rank 6, `research-lookup` at rank 8),
"integration" (Benchling, DNAnexus, LabArchives, Zarr), "variants" (GWAS,
protein and 1000 Genomes variants), "lineage" (`lamindb`, `scvelo`) and
"trajectory" (MD, quantum trajectories). None of these cost a reach.

**Scoring has no rarity weight.** A name hit scores 3 and a description hit
1, whatever the word. In `simpy` a1, "discrete-event" hits only `simpy`, but
it scored the same as "clinic", which hits 10 skills. Not tested.

**Tool-schema confusion, once.** In `scientific-brainstorming` a1 the model
passed a guessed skill name as `profile`. The tool answered "No profile" and
ignored the query. The model searched again and reached rank 1. 1 of 183
calls.

**Candidate changes.** Each was tested offline with `whatif.mjs` on patched
copies, on all 183 real queries, the 162 probe tasks, the
`scripts/test-search.mjs` suite and held-out paraphrases. The repo was not
changed.

| Variant | `esm` queries in top 8 | Held-out `esm` paraphrases | Real targets lost | Suite failures | Probe tasks better / worse |
|---|---|---|---|---|---|
| base | 0/5 | 0/6 | 0 | 0 | 0 / 0 |
| A: new `esm` trigger alias from the run's queries | 5/5 | 0/6 | 0 | 0 | 1 / 0 |
| K: `esm` index keywords from its SKILL.md | 5/5 | 5/6 | 0 | 0 | 1 / 1 |
| D2: narrow the "references" trigger | 0/5 | 0/6 | 0 | 0 | 5 / 0 |
| K + D2 | 5/5 | 5/6 | 0 | 0 | 6 / 1 |

- K's one worse probe task is `gget` (rank 2 → 3, synthetic query, still in
  the top 8). On real queries, K moves `umap-learn`'s first query from 11 to
  12, outside the limit both times.
- K + D2 on real queries: `astropy` 6 → 2, `geopandas` 6 → 2,
  `folklore-variant-evidence` 2 → 1, `relsa-severity-assessment` 3 → 1, and
  the 5 `esm` queries from not listed to ranks 1–6.
- A fits this run's wording only (0 of 6 paraphrases), so K is the better
  fix for `esm`.

**Recommendations, in order of evidence:**

1. **K: index keywords for `esm`,** from its own SKILL.md, in a package-side
   map. It fixes the only valid fail offline. New mechanism, so a design
   decision. The upstream `esm` description is not ours to change.
2. **D2: narrow the "references" trigger** to literature phrases. It needs
   fresh literature queries before it lands, because its phrases were chosen
   after the agent saw its test queries.
3. **Regression queries** in `scripts/test-search.mjs` from real model
   queries: `esm`, `astropy`, `geopandas`, the literature guards, and a
   "must not rank first" check.
4. **A `promptSnippet` for `sci_find`, and wider examples in its
   description,** that say when to search: before writing code, installing
   a tool or setting up a service for a scientific task. Today's two
   examples are both analysis tasks. Five attempts named `sci_find` and still built first, so a snippet
   that only says the tool exists may not be enough. It needs a live A/B
   run on the no-search probes (`exploratory-data-analysis`, `matlab`,
   `modal`, `open-notebook`, `parallel-web`, `polars`, `pysam`,
   `pytorch-lightning`, `qutip`, `fluidsim`, `dask`, `genomic-intelligence`:
   the 12 valid probes with a no-search attempt).
5. **Hypotheses to test offline next:** rarity (IDF) weighting, with the same
   `whatif.mjs` gates; and a `profile` value that is not a profile falling
   back to the query.
